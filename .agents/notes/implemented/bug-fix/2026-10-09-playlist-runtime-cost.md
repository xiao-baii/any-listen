# Agent Note: 播放队列持久化与列表、音源缓存开销

Status: implemented

## Problem

播放队列更新先写旧歌曲记录，再改内存，重开后更新丢失。封面读取会加载完整歌单，批量更新和删除存在重复线性扫描。公共音源文件仅在替换或关闭时清理，长期运行会积累闲置文件。

## Decision

队列歌曲更新按 itemId 写入新值，成功后改内存，保持顺序、来源和播放状态。封面冷读取按原排序只查前四首，不填充完整缓存；批量更新只为本批涉及的已缓存歌单建立临时 ID 映射，批量删除使用 Set。

临时 ID 映射按输入更新数据建立，再扫描相关缓存歌单，重复 ID 以最后一项为准；不为整张歌单建索引或加载未缓存歌单。队列更新直接构造 SQL 使用的六个字段，不通过完整队列序列化。封面和基础信息更新复用 getListMusics 的缓存写入，不重复 set。

公共音源 writeProxyCache 文件闲置 48 小时过期，每 10 分钟清理。有效读取续期，读取中的文件不删除；过期地址返回 404。账号文件地址映射访问续期，保留数量限制。清理仅覆盖公共缓存，不覆盖图标或草稿；停止音源时停止定时器并排空清理。没有磁盘硬上限、配置入口或通用缓存框架。

## Alternatives considered

为整张缓存歌单建立索引能直接逐项查找更新目标，但单首封面更新也会分配整张歌单的索引；改为索引本批输入，保留线性扫描并减少少量更新时的分配。复用完整队列序列化省去字段列举，但会复制和计算 SQL 不使用的队列属性，因此收窄内部更新参数。

全量读取直接复用现有查询且代码最少，但只为封面解析整张歌单浪费数据库和分配开销，因此保留返回四首的契约并限量查询。

容量上限实现简单并能限制磁盘总量，但会拒绝新增资源；本轮采用用户选择的闲置过期淘汰。

跟踪每个账号持有的全部文件引用能够精确管理地址生命周期，但会把资源映射变成跨账号所有权系统；这里只保护正在读取的流，允许闲置旧地址过期。

## Testing

三处局部精简后重新运行数据库 7 项、播放器 7 项、歌单/代理 9 项、歌手/前端队列 6 项，共 29 项通过；账号类型检查、Web 和桌面源码构建通过。新增冷／热缓存测试验证封面和基础信息更新的缓存引用、封面保留及重新读取后的持久化。公共音源和账号集成未在这轮重跑，下列 45 项记录属于前一轮完整实现。

固定 2000 首缓存歌单，沿用下述采样口径并包含 SQLite 写入：更新 1 首为 0.10 → 0.11 ms、20 首为 0.17 → 0.13 ms、2000 首为 3.98 → 4.02 ms。该次对照没有证明稳定的耗时改善；确定的变化是少量更新不再创建包含 2000 首的索引，队列更新不再构造 SQL 未使用的字段。

数据库 6 项、播放器 7 项、歌单/代理 9 项、公共音源 2 项、歌手/前端队列 6 项、账号集成 15 项通过，共 45 项。新增检查覆盖重开持久化、SQL 失败内存不变、同曲不同队列项隔离、重复 ID、封面冷读取不解析第五行、不填充完整缓存及更新保留对象引用。

缓存测试使用模拟时间覆盖续期、过期、正在读取、图标、文件已缺失和停止清理；实际账号网关验证有效文件 200、跨账号 403、过期地址 404。

账号 TypeScript 检查及 Web、桌面源码构建通过。构建仍输出 import.meta、Svelte 状态捕获及大 chunk 等告警，未扩大到全仓修复。

本机固定样本使用同一临时数据库、预热一次后测量十次，取排序后第六个值：10000 首歌单封面冷读取 8.79 → 3.28 ms，2000 首已缓存歌曲批量更新 8.57 → 3.95 ms。批量更新包含 SQLite 写入；查询仍需执行原排序，不宣称复杂度变为常数。这是一次本机对照，不代表生产性能保证。复现脚本保留在被忽略的 work/audit-benchmark.cjs。

## Consequences

闲置期限不是磁盘硬上限；过期地址需重新获取。历史已丢失更新不能恢复，真实音源长期播放未验收。

没有新增依赖、配置或数据迁移。清理只保护正在读取的流，文件最后一次读取结束后重新开始计算空闲期；删除失败记录日志，下一次定时清理再处理。写入和清理排空沿用音源停止流程。
