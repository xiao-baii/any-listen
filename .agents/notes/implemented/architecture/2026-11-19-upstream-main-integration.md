# Agent Note: 上游 8f6e7464 与多用户歌单适配

Status: implemented

## Problem

上游修复了歌单曲数、播放全部、设备权限和在线歌单的首次拉取。多用户有独立的歌单服务、同步队列和设备偏好，歌手筛选和分页也使用独立播放入口。

## Decision

`createMusicList` 按实例批量通知曲数。歌曲操作写库后合并 500 ms 内的歌单 ID，串行查询并用 `list_update` 通知界面。关闭实例时取消待通知的批次，等待已开始的查询结束再释放数据库。

「播放全部」和「随机播放」共用 `handlePlay`。普通歌单仅在单曲循环或不循环时切到列表循环。歌手筛选使用点击时的可见列表，在线歌手继续由分页入口建立队列。Web 输出设备偏好存于账号级 `localStore`。权限请求错误由设置页提示，授权后等待设备列表刷新。

带来源的在线歌单和榜单在创建成功后复用账号同步队列拉取一次。设置更新和定时任务按 `autoSync` 调度。首次拉取失败保留收藏，并记录错误供排查，用户可从现有入口手动同步。回包沿用歌单快照校验。

合并后的锁文件使用上游已有的 `semver` 解析，保留分支原有的 `spinnies` 完整性记录。

## Alternatives considered

直接复用上游歌单实现可以减少适配代码，计数和首次拉取会停留在单用户路径。将批次与同步任务放在账号实例内，可以沿用已有数据库和任务关闭流程。

收藏时等待源请求完成可立即显示歌曲。网络或音源故障会阻塞收藏，因此在保存之后后台拉取。

## Testing

Node 24 和 pnpm 10 的冻结安装、账号类型检查、Multi User CI 的本地检查步骤以及 Web 和桌面源码构建通过。使用两个 SQLite 账号验证加歌、删歌和移动的曲数隔离，并覆盖关闭时排空计数查询、首次拉取失败和手动重试、自动同步取消、歌手跨页和三类设备权限场景。

旧测试数据卷副本在构建出的 Web 服务上两次启动成功，账号可登录，原有歌单和曲目一致。Chrome 验证了普通歌单播放模式切换、歌手筛选循环和随机播放。本机缺少 Docker 运行时，容器内验证待执行。

## Consequences

界面曲数等待一个批次后刷新。收藏带来源的在线歌单会发起一次源请求，后续自动同步由用户设置控制。两者沿用现有事件、RPC 和数据库格式。
