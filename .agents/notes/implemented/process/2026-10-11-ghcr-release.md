# Agent Note: GHCR 发布与 1Panel 更新

Status: implemented

## Problem

当前工作流导出镜像文件，部署需手动下载和导入，无法直接使用 1Panel 的拉取与重建操作。服务器通过 GHCR 专用镜像服务访问镜像。

## Decision

正式 multi-user-vX.Y.Z 标签检查通过后发布公开 GHCR 镜像，保留固定版本及提交标签，滚动 multi-user 标签只向更高正式版本推进。固定标签不覆盖，发布任务串行执行，网络及鉴权错误不得视为标签不存在。手动执行只构建验证，预发布与普通提交只检查。

直接修改 compose.image.yml 使用滚动镜像名，保留部署项目、数据和日志挂载；删除镜像文件产物及版本环境变量。用户选择在仓库编排内直接使用 ghcr.nju.edu.cn/xiao-baii/any-listen:multi-user，发布目的地仍为官方 GHCR；不实现升级脚本、网页更新器或自动恢复。

部署文档统一为 docs/ghcr-deployment.md，所有仓库内链接同步更新。旧版本变量仅在迁移说明中保留删除提示；compose.multi-user.yml 仍用于源码构建，构建环境文件和业务配置保留。

CI 的 scripts/ghcr-release.cjs 使用 Node 内置 fetch 读取注册表清单和配置，校验摘要、linux/amd64、版本及提交标签；只有明确的注册表不存在响应才允许新建标签。相同版本与提交的完整重跑复用镜像，部分发布或冲突失败关闭；同一提交不另发其他版本。滚动标签按三段整数版本比较，更新后再次验证摘要。GitHub 并发组保证单个发布运行，可能被取消的排队任务可重跑。固定标签保护限于此发布工作流，维护者不得在其他入口改写标签。

检索活跃笔记后，歌手播放笔记仅部分重叠（描述已有 CI 检查），保留其检查契约；main 集成和数据库修复笔记不涉及发布决策。现有部署与安全文档的镜像文件流程由本决定替换，同批更新。

## Alternatives considered

镜像文件分发无需注册表连通，适合离线环境；用户明确要求删除这条流程，统一使用 GHCR。宿主机升级脚本能自动备份和恢复，但用户选择直接使用 1Panel，因此维护备份及恢复操作说明即可。容器内更新器可以网页升级程序，但增加程序与运行环境的版本协调成本，未采用。

## Testing

node --test scripts/ghcr-release.test.cjs 的 9 项测试通过，覆盖正式标签识别、数字版本比较、初次发布、重复发布、旧版本补发、固定标签冲突、部分发布、滚动标签异常、鉴权失败、摘要和架构校验及更新后的摘要验证。YAML 解析和静态配置检查通过，验证发布权限范围、编排镜像及旧产物步骤移除；npm run verify-notes 和 git diff --check 通过。

## Consequences

首次发布后需要将 GHCR 包设为公开并验证匿名拉取。linux/amd64 保持现状；代理缓存和实际 1Panel 操作需服务器验收。入口健康不代表账号及播放正常，升级需停服备份数据并保留旧镜像记录；失败恢复可能丢失备份后的写入。

multi-user-v0.1.7 发布前本地验证共 61 项测试通过（含注册表、歌手、数据库、播放器、歌单、公共音源、账号、启动及官方扩展），账号 TypeScript 检查、Web 和桌面源码构建通过。本机 pnpm 包装器尝试重新安装依赖，改用现有 ts-node 和 tsc 入口完成同等验证；先构建 Web 后，依赖其 Worker 的音源测试通过。

本地没有 Docker，未执行 Linux 容器升级和服务器代理验收；注册表单元测试使用替身，不代表外部部署已验证。真实镜像构建与推送由正式标签触发 CI。
